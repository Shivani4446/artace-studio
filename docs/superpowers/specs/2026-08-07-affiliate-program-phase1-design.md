# Affiliate Program — Phase 1: Attribution Core — Design

## Context

This is Phase 1 of a multi-phase affiliate program (researched against
`exoticindiaart.com/affiliate-program`, found to be thin — flat 10%
commission, no stated cookie window, no tiers, no FAQ — and deliberately
designed to do better: a real cookie window, tiered commissions, India-first
payout expectations, and a program built to reward genuine content over
banner-link spam for SEO value). Full phasing, agreed with the user:

1. **Attribution core** (this spec) — referral links, cookie tracking,
   linking an order back to the referring affiliate at checkout.
2. Affiliate-facing surfaces — signup/application, approval, a dashboard.
3. Commission ledger + payout tooling (admin-reviewed, manual payouts —
   no payment-gateway payout integration).
4. The public `/affiliates` landing page.

Phase 1 deliberately does **not** build the public signup form (Phase 2)
or the payout/admin ledger UI (Phase 3). It builds the plumbing that
everything else depends on: can a click be correctly attributed to an
affiliate, and does a resulting order correctly generate a commission
record? Test affiliate records for Phase 1's own verification are created
directly in Supabase, the same way every other new table in this project
ships — as a `.sql` file plus manual rows, not a UI.

Two facts, already confirmed against the live codebase before writing this
spec:

1. **Affiliate identity reuses the existing customer account system.** The
   site's auth (`utils/auth.ts`) is WordPress/WooCommerce JWT-based;
   `session.user.id` is the same id already used as `customer_id` when
   creating WooCommerce orders. An "affiliate" is a new Supabase row keyed
   to that same id — no new login system, per the user's decision.
2. **`middleware.ts` currently only runs on `/dashboard` and
   `/account`** (`config.matcher: ["/dashboard/:path*", "/account/:path*"]`),
   enforcing auth redirects. Referral-cookie capture needs to run on
   *every* page (an affiliate might link to any product, not just a fixed
   landing page), so this plan broadens the matcher and adds a second,
   independent concern to the same middleware function — without changing
   its existing auth-gating behavior for `/dashboard`/`/account`.

## Decisions

### 1. Data model (Supabase)

```sql
affiliates
  id                  BIGINT PK
  wp_customer_id      TEXT UNIQUE NOT NULL   -- same id as session.user.id
  referral_code       TEXT UNIQUE NOT NULL
  full_name           TEXT NOT NULL
  email               TEXT NOT NULL
  status              TEXT NOT NULL DEFAULT 'pending'  -- pending|approved|rejected|suspended
  commission_rate     NUMERIC NOT NULL DEFAULT 0.10     -- 0.10 / 0.12 / 0.15
  created_at, updated_at

affiliate_clicks
  id                  BIGINT PK
  affiliate_id        BIGINT FK -> affiliates.id
  landing_path        TEXT NOT NULL
  user_agent          TEXT
  ip_address          TEXT
  clicked_at          TIMESTAMP DEFAULT NOW()

affiliate_conversions
  id                  BIGINT PK
  affiliate_id        BIGINT FK -> affiliates.id
  wc_order_id         BIGINT NOT NULL
  order_total         NUMERIC NOT NULL
  commission_rate_applied NUMERIC NOT NULL
  commission_amount   NUMERIC NOT NULL
  status              TEXT NOT NULL DEFAULT 'pending'  -- pending|approved|paid|voided
  created_at, updated_at
```

`commission_rate` on `affiliates` is a plain column, manually adjustable
(direct Supabase edit for now). Automatic tier evaluation (bumping 10% →
12% → 15% based on trailing performance) is explicitly **Phase 3's**
job — Phase 1 always applies whatever rate is currently stored on the
affiliate's row at the moment of the order, which is enough to prove
attribution works correctly end to end.

### 2. Referral codes and links

- Format: `artacestudio.com/?ref=CODE` — works appended to **any** URL on
  the site (homepage, a specific product, a collection page), not a fixed
  landing page, so affiliates can link directly to what they're promoting.
- Code generation: slugified full name + a short random suffix for
  uniqueness (e.g., "priya-4f2a") — memorable, guaranteed-unique via the
  suffix, generated by a small shared utility (`lib/affiliates/codes.ts`)
  reused by Phase 2's signup flow later.

### 3. Attribution capture — extending `middleware.ts`

- Matcher broadens from `["/dashboard/:path*", "/account/:path*"]` to run
  on all page routes (excluding `/api`, `/_next`, and static assets via
  the standard Next.js middleware exclusion pattern).
- New, independent logic added alongside the existing auth check (not
  replacing it): if the incoming request's URL has a `ref` query param,
  set a cookie `artace_ref` (value = the code, `maxAge` 60 days, `path=/`,
  not `httpOnly` since no server-only secret is involved) on the response.
  **Last click wins** — a new `?ref=` always overwrites whatever code was
  previously stored.
- The existing `/dashboard`/`/account` auth-redirect logic is untouched —
  this is an additive branch in the same function, verified by the
  existing behavior still working exactly as before (see Verification).

### 4. Checkout-time attribution — extending `lib/api-route-handlers/checkout/route.ts`

After a WooCommerce order is successfully created (existing code, this
plan only adds a step after that point, not before):

1. Read the `artace_ref` cookie from the incoming request.
2. If present, look up a matching, `status = 'approved'` row in
   `affiliates` by `referral_code`. A missing/unapproved/unknown code is
   silently ignored — checkout must never fail or be delayed because of a
   bad or stale referral cookie.
3. If a valid affiliate is found:
   - Add `{key: "Referred By", value: affiliate.referral_code}` to the
     order's `meta_data` (same established mechanism as the existing
     `Frame`/`Order Type` tags — visible directly in the WooCommerce
     admin order screen, no new admin tooling needed for Phase 1).
   - Insert one row into `affiliate_conversions`: `wc_order_id` from the
     just-created order, `order_total` = `wooOrder.total`,
     `commission_rate_applied` = the affiliate's current `commission_rate`,
     `commission_amount` = `order_total * commission_rate_applied`,
     `status = 'pending'`.
4. None of this blocks or fails the checkout response — if the Supabase
   insert fails, the order still completes normally and the failure is
   logged, not surfaced to the customer. Losing one commission record to
   a transient failure is an acceptable, recoverable gap; failing a
   customer's real purchase because of it is not.

## Data flow

1. Visitor clicks `artacestudio.com/shop/some-painting?ref=priya-4f2a`.
2. `middleware.ts` sets `artace_ref=priya-4f2a` (60-day cookie) alongside
   its existing, unmodified auth check.
3. Visitor browses, leaves, returns within 60 days, completes checkout.
4. `checkout/route.ts` creates the WooCommerce order as it already does,
   then reads `artace_ref`, finds the matching approved affiliate, tags
   the order, and inserts the `affiliate_conversions` row.
5. Nothing in Phase 1 reads `affiliate_conversions` back out yet — that's
   Phase 3's ledger/payout UI. Phase 1 verification reads it directly via
   Supabase to confirm correctness.

## Error handling

- Malformed/unknown/unapproved referral codes are silently ignored at
  checkout — never an error state visible to the customer.
- Supabase insert failures at checkout are caught and logged, never
  allowed to fail or delay order creation — the same fail-safe posture
  already established for `unitPrice` overrides in the Prints checkout
  work (a missing enhancement degrades gracefully; a broken checkout does
  not).
- Middleware's new referral-cookie branch runs independently of the
  existing auth-redirect branch — an error setting the referral cookie
  must never block or redirect a request that the auth check would
  otherwise have allowed through.

## Out of scope (this phase)

- No public signup/application form (Phase 2).
- No affiliate dashboard (Phase 2).
- No admin approval UI — approving an affiliate in Phase 1 means manually
  setting `status = 'approved'` in Supabase.
- No automatic tier evaluation (Phase 3).
- No refund clawback automation (Phase 3) — a refunded order's commission
  row is not automatically voided in Phase 1.
- No payout processing of any kind (Phase 3, manual even then).
- No `/affiliates` marketing page (Phase 4).

## Standing project constraints (carried forward)

- No `git commit`/`git push` — the user reviews and commits/pushes
  everything themselves.
- No test framework — verification via `npx tsc --noEmit`, plus a safe
  isolated WooCommerce test order (created via the Admin API with
  `set_paid: false`, verified, then deleted — the same pattern already
  proven for the Prints checkout fix) rather than a real Razorpay payment,
  since this account has no test/sandbox mode.
- Given the port-3000 incident: no `npm run build` / `rm -rf .next` while
  port 3000 may be running; check first, never touch that PID.
