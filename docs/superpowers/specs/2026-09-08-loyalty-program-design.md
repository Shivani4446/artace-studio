# Artace Rewards (Loyalty Program) — Design

## Context

The user asked to build a loyalty/rewards program — the first of three Section
3 features from `suggestion.md`, in this order: Loyalty → Gift Cards → "View
in Your Room." Referral is considered already covered by the existing
affiliate program (`app/affiliates`, `app/dashboard/affiliate`) and is out of
scope here.

Confirmed with the user before writing this spec:

- **Program name**: "Artace Rewards" in all customer-facing copy.
- **Build approach**: fully custom (Supabase-backed), matching the affiliate
  program's pattern — no WooCommerce loyalty plugin.
- **Earning**: 1 point per ₹100 of an order's paid total, floored (no partial
  points). Every completed order earns points on its full amount — no
  exclusions for sale items, categories, or order types.
- **Redemption**: 1 point = ₹1 discount. Minimum 100 points (₹100) before a
  customer can redeem anything — i.e., redemption unlocks after ₹10,000
  cumulative spend.
- **No expiry**, for now.
- **Redemption mechanism**: a dedicated "Apply Reward Points" control at
  checkout, independent of the coupon system (so it can stack with a real
  coupon) — not a generated WooCommerce coupon code.
- **Crediting timing**: points are credited the moment payment is verified
  (same moment the order is confirmed today), and automatically clawed back
  if that order is later refunded or cancelled.
- **Scope**: the main Artace cart checkout, plus Samora's checkout as of the
  Samora infra-reuse follow-up (see §9) — Samora was originally meant to be
  out of scope for this build, but the crediting code was never actually
  gated by `storeName`, so it was earning points regardless; the user chose
  to formalize that rather than fix it, and redemption was added to match.
  Custom Portraits deposits remain out of scope.
- **Public page**: yes, a dedicated `/rewards` explainer page, linked from the
  navbar and footer, on the sitemap.

One accepted, explicitly-flagged edge case: if the same customer completed
two orders redeeming overlapping points within the same second or two, there
is a small race window before both ledger writes land, since balance is
recomputed fresh per request rather than locked. Not engineered around here —
revisit only if real usage ever makes it a real problem.

Two real gaps found while researching this spec against the existing
checkout code (not assumptions — verified by reading the files):

1. `WooOrderSummary`/`parseWooOrderSummary` in `utils/woocommerce-checkout.ts`
   currently does **not** expose `customer_id` or `line_items` from the
   WooCommerce order payload — both are required for this feature (to know
   who to credit, and to exclude non-qualifying orders) and don't exist
   today. This needs a small, additive extension to that shared parser,
   detailed below.
2. `/api/checkout/verify` is **reused by the Custom Portraits deposit flow**
   (same endpoint, per `components/custom-portraits/CustomPortraitForm.tsx`).
   Since this build's scope is the main checkout only, the points-crediting
   logic added there must positively exclude Custom Portraits orders, not
   assume it never sees one.

## Decisions

### 1. Data model

New file: `supabase/rewards_ledger.sql` (the user runs this in the Supabase
SQL editor, same pattern as every other Supabase table this engagement):

```sql
CREATE TABLE IF NOT EXISTS rewards_ledger (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  wp_customer_id TEXT NOT NULL,
  wc_order_id BIGINT,
  points INTEGER NOT NULL,
  type TEXT NOT NULL, -- 'earn' | 'redeem' | 'clawback'
  description TEXT NOT NULL,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

CREATE INDEX IF NOT EXISTS rewards_ledger_customer_idx ON rewards_ledger (wp_customer_id);

ALTER TABLE rewards_ledger ENABLE ROW LEVEL SECURITY;
```

Naming (`wp_customer_id`, `wc_order_id`) matches `supabase/affiliate_program.sql`
exactly, for consistency. `points` is a signed integer — positive for `earn`,
negative for `redeem`/`clawback`. A customer's balance is always
`SUM(points) WHERE wp_customer_id = ?` — computed on read, never stored
redundantly.

### 2. Shared rewards utility — `lib/rewards/`

- `lib/rewards/constants.ts` — `POINTS_PER_RUPEE_SPENT = 0.01` (i.e. 1 point
  per ₹100), `POINT_VALUE_INR = 1`, `MIN_REDEMPTION_POINTS = 100`, and
  `PROGRAM_NAME = "Artace Rewards"` so copy stays consistent everywhere it's
  used.
- `lib/rewards/ledger.ts` — thin Supabase REST helpers matching the existing
  `findApprovedAffiliateByCode`/`recordAffiliateConversion` pattern in
  `lib/api-route-handlers/checkout/route.ts` (same `SUPABASE_URL`/
  `SUPABASE_SERVICE_ROLE_KEY` env resolution, same fetch-based REST calls,
  not the `@supabase/supabase-js` client — matching what checkout already
  does rather than introducing a second way to talk to Supabase):
  - `getPointsBalance(wpCustomerId: string): Promise<number>` — sums the
    ledger for that customer.
  - `creditPoints({ wpCustomerId, wcOrderId, points, description })` — inserts
    an `earn` row.
  - `debitPoints({ wpCustomerId, wcOrderId, points, description })` — inserts
    a `redeem` row (caller must have already validated sufficient balance).
  - `clawbackPointsForOrder(wcOrderId: number)` — looks up the `earn` (and any
    `redeem`) rows for that order, and inserts an equal-and-opposite
    `clawback` row for each, unless a clawback already exists for that order
    (checked via a `type = 'clawback' AND wc_order_id = ?` query first, so a
    duplicate webhook delivery can't double-clawback).
  - `calculatePointsEarned(orderTotal: number): number` —
    `Math.floor(orderTotal * POINTS_PER_RUPEE_SPENT)`.

### 3. Extending `WooOrderSummary` to expose `customerId` and `lineItems`

In `utils/woocommerce-checkout.ts`:

- Add `customerId: number` and `lineItems: { productId: number }[]` to the
  `WooOrderSummary` type.
- In `parseWooOrderSummary`, add:
  ```ts
  customerId: ensurePositiveInt(payload.customer_id) || 0,
  lineItems: Array.isArray(payload.line_items)
    ? payload.line_items
        .map((item) => ensurePositiveInt((item as { product_id?: unknown }).product_id))
        .filter((id): id is number => id !== null)
        .map((productId) => ({ productId }))
    : [],
  ```
- Add `customer_id?: unknown; line_items?: unknown;` to the `WooOrderPayload`
  type these are parsed from.

This is additive only — every existing caller of `getWooCommerceOrder`/
`parseWooOrderSummary` ignores fields it doesn't ask for, so nothing already
built breaks.

### 4. Earning + redemption in the checkout flow

**At `/api/checkout` (`lib/api-route-handlers/checkout/route.ts`)** — accept
a new optional field on `CheckoutRequestBody`:

```ts
pointsToRedeem?: number;
```

After the existing `customerId` is resolved (line ~266) and before building
`feeLines`:

1. If `pointsToRedeem` is a positive integer, re-fetch the real balance via
   `getPointsBalance(String(customerId))` — **never trust the client's
   number.** Reject with 400 if `pointsToRedeem > balance`, or if
   `0 < pointsToRedeem < MIN_REDEMPTION_POINTS`.
2. If valid and `> 0`, add a `fee_lines` entry:
   `{ name: "Artace Rewards Discount", total: (-pointsToRedeem * POINT_VALUE_INR).toFixed(2) }`
   — appended to the existing `feeLines` array (which today only Samora's
   gift-wrapping fee populates; Artace checkout's `feeLines` starts empty, so
   this is the first thing that can populate it for a non-Samora order).

   **Flagging honestly, not asserting false confidence**: a negative
   `fee_lines.total` is a commonly-documented WooCommerce technique for an
   arbitrary discount, but every existing use of `fee_lines` in this codebase
   (Samora's gift-wrap fee) is positive — this exact negative-value path has
   not been exercised against this store's real WooCommerce instance. The
   implementation plan should verify this against a real test order (a small
   `wc/v3/orders` POST/PUT with a negative fee line, checked in wp-admin)
   *before* wiring it into the live checkout flow, not assume it from
   general WooCommerce knowledge. If it doesn't reduce the total as expected,
   the fallback is proportionally reducing each line item's own `total`
   instead (messier — needs distributing the discount across multiple line
   items — but a known-working alternative).
3. After the order is created, stash the intent in order meta (alongside the
   existing `_artace_razorpay_order_id` etc. in the `updateWooCommerceOrder`
   call): `_artace_points_to_redeem: String(pointsToRedeem)`. Nothing is
   debited from the ledger yet — that happens at verify time, matching how
   earning already works.

**At `/api/checkout/verify` (`lib/api-route-handlers/checkout/verify/route.ts`)**
— crediting/debiting must only run the *first* time an order is finalized,
never on a retried verify call for an already-paid order. The existing code
already distinguishes these two cases via its `finalizedOrder` ternary
(line ~76-94): the `wooOrder` branch (no `updateWooCommerceOrder` call) means
this order was already marked successful in an earlier call — skip points
entirely there. Only the `await updateWooCommerceOrder(...)` branch is a
genuine first-time finalization; add the crediting/debiting steps below
right after that branch resolves, inside that branch only:

1. **Exclude non-qualifying orders first**: skip all of the below entirely if
   `wooOrder.lineItems.some(item => item.productId === CUSTOM_PORTRAIT_DEPOSIT_PRODUCT_ID)`
   (import the same constant from `lib/api-route-handlers/custom-portraits/route.ts`,
   or hoist it to a shared location — implementer's call) or if
   `wooOrder.customerId` is `0` (a guest order has no account to credit).
2. Credit: `creditPoints({ wpCustomerId: String(wooOrder.customerId), wcOrderId: orderId, points: calculatePointsEarned(Number(wooOrder.total)), description: \`Order #${wooOrder.orderNumber}\` })`.
3. Debit (if `_artace_points_to_redeem` is present in `wooOrder.metaData` and
   `> 0`): `debitPoints({ wpCustomerId: String(wooOrder.customerId), wcOrderId: orderId, points: <that value>, description: \`Redeemed on Order #${wooOrder.orderNumber}\` })`.
4. Both are best-effort, non-blocking — wrap in try/catch so a Supabase
   hiccup never fails the customer's actual payment verification (same
   defensive posture as `recordAffiliateConversion`'s own comment: "Never let
   a commission-logging failure affect the checkout response").

### 5. Refund/cancellation clawback webhook

New route: `lib/api-route-handlers/webhooks/woocommerce-order-status/route.ts`
(registered in `app/api/[[...path]]/route.ts` per the existing alphabetized
`ROUTES` map convention), modeled structurally on
`lib/api-route-handlers/razorpay/webhook/route.ts`:

- WooCommerce signs webhook payloads with `X-WC-Webhook-Signature`
  (base64 HMAC-SHA256 of the raw body, using the webhook's configured
  secret) — verify this the same way `verifyRazorpayWebhookSignature`
  verifies Razorpay's, against a new `WOOCOMMERCE_ORDER_WEBHOOK_SECRET` env
  var (added to `.env.example`).
- Payload is the full WooCommerce order object (topic: `order.updated`).
  If `payload.status` is `refunded` or `cancelled`, call
  `clawbackPointsForOrder(payload.id)`.
- Every other status transition is ignored (`{ ok: true, ignored: true }`) —
  this webhook only ever removes points, never grants them (granting stays
  exclusively in `/api/checkout/verify`, so there's one source of truth for
  "why did this customer get points").

**Manual setup step for the user, after this is built** (same pattern as
being asked to run a `.sql` file): create the webhook in WordPress admin —
WooCommerce → Settings → Advanced → Webhooks → Add webhook. Topic: "Order
updated". Delivery URL: `https://artacestudio.com/api/webhooks/woocommerce-order-status`.
Secret: the same value set as `WOOCOMMERCE_ORDER_WEBHOOK_SECRET`. Exact
screenshot-level steps will be handed over once this is built, not guessed
at now.

### 6. Checkout UI — "Apply Reward Points"

In `app/checkout/checkout-client.tsx`, a new box in the `<aside>` sidebar,
placed after the existing "Have a coupon?" box (around line 631) and before
the pay button:

- Fetches the customer's current balance on mount (a new lightweight GET
  endpoint, `lib/api-route-handlers/rewards/balance/route.ts` → `/api/rewards/balance`,
  requiring the same auth session `/api/checkout` already requires — returns
  `{ balance: number }`). Registered in `app/api/[[...path]]/route.ts`'s
  `ROUTES` map alongside the other new routes this feature adds
  (`rewards/balance`, `rewards/history`, `webhooks/woocommerce-order-status`),
  same alphabetized-import convention as every existing entry there.
- If `balance < MIN_REDEMPTION_POINTS`: shows the balance and how many more
  points are needed to unlock redemption ("You have 40 points — earn 60 more
  to redeem your first reward"), no input control.
- If `balance >= MIN_REDEMPTION_POINTS`: a number input (or a simple
  increment control), capped at `Math.min(balance, Math.floor(subtotal))`
  points, with a live "− ₹{pointsToRedeem} applied" preview and an
  "Apply"/"Remove" toggle matching the existing coupon box's interaction
  pattern. The chosen `pointsToRedeem` value is included in the
  `handleCheckout` POST body.

### 7. Account dashboard — `/dashboard/rewards`

New page, sibling to `app/dashboard/affiliate/page.tsx` and
`app/dashboard/orders/page.tsx`, following the same `DashboardShell`
wrapper pattern already established there:

- Current balance and its ₹ value.
- A history table sourced from a new `lib/api-route-handlers/rewards/history/route.ts`
  → `/api/rewards/history` endpoint
  (`{ entries: { date, description, points, type }[] }`, most recent first)
  — date, description (from the ledger's `description` column), points
  (signed, `+45` / `−100`), and a running balance column computed client-side
  from the entries.
- A short rules recap (earn rate, redemption rate, minimum) linking to the
  full `/rewards` page for details.

### 8. Public page — `/rewards`

New top-level route, structured like `/trade` or `/art-care` (hero,
explainer sections, `FAQSection`, sign-in/sign-up CTA):

- Hero: "Artace Rewards" — the program name, a one-line pitch.
- "How it works": earning (1 point per ₹100 spent) and redemption (1 point =
  ₹1, minimum 100 points) — the real, confirmed numbers, nothing invented.
- FAQ via the existing `FAQSection` component (matching every other marketing
  page this engagement) — questions like "How do I check my balance?", "Do
  points expire?" (answer: no, for now), "Can I combine points with a
  coupon?" (answer: yes).
- CTA: "Sign in to see your rewards" / "Create an account" depending on auth
  state.

Added to: `components/navbar.tsx` (Resources dropdown — the same one
`/art-care`, `/exhibition`, `/team` etc. live in), the footer, and
`app/sitemap.ts`'s static pages array.

### 9. Explicitly out of scope for this build

- Custom Portraits deposits — noted in Context above.
- ~~Samora's checkout~~ — **done**: `ApplyPointsBox` was added to
  `app/samora/checkout/checkout-client.tsx`, reusing the same component,
  `/api/rewards/balance` endpoint, and ledger as the main checkout. See the
  Context note above for why (points were already being credited on Samora
  orders regardless of this doc's original scope statement).
- Point expiry, tiers, and bonus-earning rules (first order, referrals,
  reviews) — none of these were asked for; adding them speculatively would
  be scope creep beyond what was decided.
- A WooCommerce coupon-based redemption path — explicitly rejected in favor
  of the independent "Apply Points" control (Decision 4 above).

## Manual setup after this is built

1. Run `supabase/rewards_ledger.sql` in the Supabase SQL editor.
2. Add `WOOCOMMERCE_ORDER_WEBHOOK_SECRET` to `.env.local` (and to Cloudflare
   Pages' environment variables for production) — a real random secret, not
   a placeholder.
3. Create the WooCommerce webhook (Settings → Advanced → Webhooks) per
   Decision 5 above, using that same secret.
4. Real end-to-end verification on your own live server (not this sandbox,
   same caveat as every other payment flow this engagement) — place a real
   order, confirm points appear; issue a real refund, confirm they're
   clawed back.
