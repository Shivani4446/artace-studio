# Gift Cards — Design

## Context

Second of the three Section 3 features from `suggestion.md`, in the agreed order: Loyalty (done) → Gift Cards (this) → "View in Your Room."

Confirmed with the user before writing this spec:

- **Customers can purchase gift cards** — a real, sellable product, not just an internal/admin-issued tool.
- **Fixed denominations only**: ₹1,000 / ₹2,500 / ₹5,000 / ₹10,000. No custom-amount entry.
- **Redemption is code-based**, not tied to any account — the classic model. A purchaser buys a card, gets a code, gives it to anyone; the recipient enters the code at checkout. No account needed to hold or redeem a card.
- **Partial redemption carries a remaining balance forward** (e.g. a ₹5,000 card spent ₹3,000 on one order still has ₹2,000 for later). This is the reason a custom ledger is needed instead of WooCommerce's native coupon system — a fixed-amount coupon reused across multiple orders would apply its full discount *every* time, not decline a balance.
- **No expiry.**
- **Delivery**: emailed to the purchaser only (not a recipient), plus shown on the confirmation screen. No recipient-details collection.
- **No refunds** on a purchased gift card, used or not.
- **Purchase flow is guest-friendly** (no account required) — approved in Section B of the design dialogue.
- **Gift card purchases don't earn Artace Rewards points** — approved in Section B, same treatment as Custom Portraits deposits.
- **A public balance-checker** (enter a code, see remaining balance) — approved in Section D.

## Decisions

### 1. Data model

New file: `supabase/gift_cards.sql`:

```sql
CREATE TABLE IF NOT EXISTS gift_cards (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  code TEXT UNIQUE NOT NULL,
  original_amount NUMERIC NOT NULL,
  remaining_balance NUMERIC NOT NULL,
  purchaser_email TEXT NOT NULL,
  wc_order_id BIGINT,
  status TEXT NOT NULL DEFAULT 'active', -- 'active' | 'depleted'
  created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

CREATE INDEX IF NOT EXISTS gift_cards_code_idx ON gift_cards (code);

CREATE TABLE IF NOT EXISTS gift_card_redemptions (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  gift_card_id BIGINT NOT NULL REFERENCES gift_cards(id),
  wc_order_id BIGINT NOT NULL,
  amount_redeemed NUMERIC NOT NULL,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

ALTER TABLE gift_cards ENABLE ROW LEVEL SECURITY;
ALTER TABLE gift_card_redemptions ENABLE ROW LEVEL SECURITY;
```

`NUMERIC` for money matches `supabase/affiliate_program.sql`'s own convention (`order_total NUMERIC`, `commission_amount NUMERIC`).

### 2. Hidden "Gift Card" WooCommerce product

Same pattern already proven for Custom Portraits (`CUSTOM_PORTRAIT_DEPOSIT_PRODUCT_ID = 4317`, created via one Admin API call, documented in `docs/superpowers/plans/2026-08-11-custom-portraits.md` Task 2) — created the same way, not by the user manually in wp-admin:

```bash
curl -s -u "$WOOCOMMERCE_CONSUMER_KEY:$WOOCOMMERCE_CONSUMER_SECRET" \
  -X POST "https://api.artacestudio.com/wp-json/wc/v3/products" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Artace Gift Card",
    "type": "simple",
    "status": "draft",
    "virtual": true,
    "sold_individually": true,
    "tax_status": "none",
    "regular_price": "1",
    "short_description": "A digital gift card. The final charge is set per order to the denomination purchased and does not reflect this product'\''s catalog price."
  }'
```

`status: "draft"` (not `"publish"`) — this store's Store API doesn't honor `catalog_visibility: "hidden"`, and draft was already verified to be the setting that actually excludes a product from the public catalog while still working for server-side Admin API order creation (same finding as Custom Portraits).

`tax_status: "none"` — set deliberately given the tax/pricing discrepancy found while testing the Loyalty program (a taxable product's line-item price came out ~12% short of its displayed price with no compensating tax line). A gift card's charged amount must be *exactly* the denomination purchased, so it can't be exposed to whatever is happening with tax calculation on regular taxable products until that's understood — this sidesteps the question entirely for this feature rather than inheriting an unresolved problem.

The resulting product id gets hardcoded as `GIFT_CARD_PRODUCT_ID` in `lib/gift-cards/constants.ts` (Decision 3), the same way `CUSTOM_PORTRAIT_DEPOSIT_PRODUCT_ID` lives in `lib/custom-portraits/pricing.ts`.

### 3. Shared gift-card utility — `lib/gift-cards/`

- `lib/gift-cards/constants.ts` — `GIFT_CARD_PRODUCT_ID` (from Decision 2), `DENOMINATIONS = [1000, 2500, 5000, 10000]`, `PROGRAM_NAME = "Artace Gift Card"`.
- `lib/gift-cards/code.ts` — `generateGiftCardCode(): string`, format `ARTACE-XXXX-XXXX-XXXX` (uppercase alphanumeric, excluding visually ambiguous characters `0/O/1/I` to reduce transcription errors when a purchaser reads a code aloud or retypes it):
  ```ts
  const ALPHABET = "ABCDEFGHJKLMNPQRSTUVWXYZ23456789"; // no 0/O/1/I
  const randomSegment = () =>
    Array.from({ length: 4 }, () => ALPHABET[Math.floor(Math.random() * ALPHABET.length)]).join("");
  export const generateGiftCardCode = (): string =>
    `ARTACE-${randomSegment()}-${randomSegment()}-${randomSegment()}`;
  ```
- `lib/gift-cards/ledger.ts` — same fetch-based Supabase REST pattern as `lib/rewards/ledger.ts` (not `@supabase/supabase-js`):
  - `createGiftCard(input: { amount: number; purchaserEmail: string; wcOrderId: number }): Promise<{ code: string }>` — generates a code, retries on the rare unique-constraint collision (checked via a `select` before insert, matching the codebase's existing `hasClawbackForOrder`-style pre-check pattern rather than trapping a Postgres error code), inserts the row, returns the code.
  - `getGiftCardBalance(code: string): Promise<{ found: boolean; remainingBalance: number; status: string }>` — used by both checkout redemption and the public balance-checker.
  - `redeemGiftCard(input: { code: string; wcOrderId: number; amount: number }): Promise<void>` — decrements `remaining_balance`, flips `status` to `'depleted'` if it reaches 0, inserts a `gift_card_redemptions` row. Re-reads the current balance immediately before writing (not the balance a caller fetched earlier in the request) to keep the same "server is authoritative, never trust a stale read" discipline as `lib/rewards/ledger.ts`.

### 4. Purchase flow — `/api/gift-cards`

New guest-friendly endpoint, `lib/api-route-handlers/gift-cards/route.ts`, structured identically to `lib/api-route-handlers/custom-portraits/route.ts` (no `getAuthSessionFromRequest` call — this is deliberately guest-friendly, matching the Context decision):

1. Accepts `{ amount: number; purchaserEmail: string; purchaserName: string }`. Validates `amount` is one of `DENOMINATIONS` exactly (reject anything else — never trust a client-supplied arbitrary amount for what becomes real spendable value).
2. `createWooCommerceOrder` with `line_items: [{ product_id: GIFT_CARD_PRODUCT_ID, quantity: 1, subtotal: amount.toFixed(2), total: amount.toFixed(2) }]` — the same `subtotal`/`total` override mechanism Custom Portraits already proved.
3. Creates the Razorpay order, stashes `_artace_razorpay_order_id` in meta — identical to Custom Portraits' own Step through this point.
4. Returns the same shape Custom Portraits returns (Razorpay config + order identifiers) for the client to open the Razorpay widget.

**No gift card row is created yet** — same timing discipline as Loyalty's crediting: nothing real happens until payment is actually verified.

### 5. Gift card generation at payment verification

`/api/checkout/verify` already special-cases orders by product id (the Custom Portraits exclusion added for Loyalty). Add one more branch there, alongside the existing Loyalty crediting block, inside the same `if (isFirstTimeFinalization)` guard:

```ts
const isGiftCardOrder = wooOrder.lineItems.some((item) => item.productId === GIFT_CARD_PRODUCT_ID);

if (isGiftCardOrder) {
  try {
    const { code } = await createGiftCard({
      amount: Number(wooOrder.total),
      purchaserEmail: wooOrder.billingEmail,
      wcOrderId: orderId,
    });
    await sendGiftCardEmail({ to: wooOrder.billingEmail, code, amount: Number(wooOrder.total) });
  } catch {
    // Never let gift-card generation/email failure affect the checkout response —
    // same defensive posture as the Loyalty crediting block right above this one.
  }
}
```

This sits as a sibling `if` to the existing `if (!isCustomPortraitOrder && wooOrder.customerId > 0)` Loyalty block — a gift card order is also excluded from that block automatically, since `isGiftCardOrder` orders don't need a separate exclusion check added to the Loyalty condition (the Loyalty condition already only fires for orders with a real logged-in `customerId`, and gift card purchases are guest orders with `customerId === 0`, so they're excluded by the *existing* `wooOrder.customerId > 0` check without any change needed there). Worth double-checking this during implementation rather than assuming: if a logged-in customer buys a gift card through this same guest-style endpoint, does the order still get `customer_id: 0` because `/api/gift-cards` never passes a `customer_id` to `createWooCommerceOrder` at all? Confirmed by reading Decision 4 above — correct, `customer_id` is never set there, so this holds regardless of whether the purchaser happens to be logged in elsewhere in the same browser.

**Email content** — real copy, not placeholder: subject `"Your Artace Gift Card"`, body includes the code, the amount, and a line noting it never expires and can be used at artacestudio.com checkout. Uses the same Resend REST call pattern as `lib/api-route-handlers/trade-leads/route.ts` (`RESEND_API_KEY`, `RESEND_FROM`, POST to `https://api.resend.com/emails`), added as `lib/gift-cards/email.ts`'s `sendGiftCardEmail`.

### 6. Redemption at the main cart checkout

**At `/api/checkout`** — accept a new optional field, `giftCardCode?: string`. Processed *after* the existing Loyalty points validation (Decision 4 of the Loyalty spec), so the two discounts can be capped correctly against each other:

```ts
let giftCardApplied = 0;
let giftCardCodeNormalized = "";

if (body.giftCardCode) {
  giftCardCodeNormalized = sanitizeText(body.giftCardCode).toUpperCase();
  const giftCard = await getGiftCardBalance(giftCardCodeNormalized);

  if (!giftCard.found || giftCard.status !== "active" || giftCard.remainingBalance <= 0) {
    return NextResponse.json({ error: "That gift card code isn't valid or has no remaining balance." }, { status: 400 });
  }

  // Cap combined discounts (points + gift card) at the order subtotal, computed
  // against the subtotal *before* fee_lines, using whatever points discount was
  // already resolved above this block — never let a customer's total go negative.
  const remainingAfterPoints = subtotalBeforeDiscounts - pointsToRedeem * POINT_VALUE_INR;
  giftCardApplied = Math.min(giftCard.remainingBalance, Math.max(0, remainingAfterPoints));

  if (giftCardApplied > 0) {
    feeLines.push({ name: "Gift Card Redemption", total: (-giftCardApplied).toFixed(2) });
  }
}
```

(`subtotalBeforeDiscounts` needs to be a real computed value from `normalizedLineItems` — the implementer should confirm the exact variable name/expression already available at this point in `lib/api-route-handlers/checkout/route.ts`, since this spec is written against the file's shape as of the Loyalty program's changes, not a fresh read of the current file.)

Stash the redemption intent in order meta the same way points redemption already does: `_artace_gift_card_code` and `_artace_gift_card_amount`, added to the same `mergeWooMetaData` call.

**At `/api/checkout/verify`** — inside the same first-time-finalization, non-Custom-Portraits, non-gift-card-purchase branch as Loyalty's debit step, read back `_artace_gift_card_code`/`_artace_gift_card_amount` from `wooOrder.metaData` and call `redeemGiftCard({ code, wcOrderId: orderId, amount })`.

**Checkout UI** — a new box, `components/checkout/RedeemGiftCardBox.tsx`, structured like `ApplyPointsBox.tsx` but simpler (no balance to fetch on mount — a gift card belongs to whoever holds the code, not the logged-in account): a code input + "Apply" button that calls a new lightweight validation endpoint (`GET /api/gift-cards/balance?code=...`, public, no auth — a gift card code is the credential, same as a coupon code) to show the amount that will be applied before the customer commits to checking out, then includes `giftCardCode` in the `/api/checkout` POST body exactly like `pointsToRedeem` already does.

Being necessarily public and unauthenticated (the code itself is the only credential a real gift card has), this endpoint is the same category of thing already flagged sitewide in `suggestion.md` §2.4 (no rate limiting on public API routes) — not a new gap introduced here, but worth remembering when that gets addressed, since the code-generation keyspace (32 possible characters × 12 random characters) makes brute-forcing impractical on its own but rate limiting is still the right defense-in-depth layer.

### 7. Public balance-checker + `/gift-cards` page

New top-level route, `app/gift-cards/page.tsx`, structured like `/rewards`:

- Hero + the four denomination cards, each linking to the purchase flow (a `GiftCardPurchaseForm` client component posting to `/api/gift-cards`, structured like `CustomPortraitForm.tsx`'s Razorpay-widget-invocation pattern).
- A "Check Your Balance" box: code input, calls the same `GET /api/gift-cards/balance?code=...` endpoint Decision 6's checkout box uses, shows the remaining balance or "not found."
- FAQ via `FAQSection` (denominations, no-expiry, no-refund policy stated plainly, how redemption works).

Added to: `components/navbar.tsx` (`resourceLinks`), `components/footer.tsx` (Shop section, next to "Artace Rewards"), `app/sitemap.ts`.

### 8. Explicitly out of scope for this build

- Recipient-direct delivery (email to someone other than the purchaser) — Context decision was purchaser-only.
- Refunds on unused cards — Context decision was no refunds.
- Custom amount entry — fixed denominations only.
- Admin-issued codes (promotions, customer service credits) outside the purchase flow — not asked for and not built. Note for a future build, not acted on now: `wc_order_id` in Decision 1's schema is nullable, which already leaves room for an admin-issued card with no purchase order behind it, without needing a schema change later.

## Manual setup after this is built

1. Run `supabase/gift_cards.sql` in the Supabase SQL editor.
2. Create the hidden "Artace Gift Card" WooCommerce product (Decision 2) — done via Admin API during implementation, not a manual wp-admin step, mirroring how the Custom Portraits product was created.
3. Real end-to-end verification on the live server (same caveat as every payment flow this engagement): purchase a real gift card, confirm the email arrives with a real code, redeem it (fully and then partially, to confirm the remaining-balance behavior) on a real order.
